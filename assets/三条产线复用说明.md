## 01 Reddit Daily

输入：原帖、作者演示、可使用的视频素材、栏目规则。

路径：检索 → 核实与筛选 → 写稿 → 配音 / 字幕 / 卡片 / 剪辑 → 发布 → 复盘写回 Skills。

分工：Codex 按 Skills 串联任务；ChatCut 承担可编辑的视频工程；数据工作台记录素材、脚本版本与发布反馈。

最重要的人工判断：这个项目哪里值得看；画面是否清晰流畅；文案和声音是否自然；品牌是否确实参与案例。涉及商业合作按平台要求标注。

复用时先准备：目标受众、固定栏目结构、三条有来源且有画面的样例、字幕和声音参考。先做一条完整样片，再改规则，不要先堆提示词。

发布进展（Kevin 2026-10-15 更新）：已发布 100 条视频，当前平均每条播放 3,000，下一阶段目标平均每条 10,000。保留的单条小红书案例为 18,200 播放、885 赞、910 收藏、121 分享、24 评论；该条按 Skills 制作约 20 分钟。

## 02 每日 3D 知识分享

主线：只解决一个核心问题——怎么把 3D 论文变得可视化。我们自建网站获取 3D 论文，自动喂给 Claude；Claude 5.5 拆解原理、写代码逻辑，three.js 呈现三维动画，让普通观众快速看懂论文解决的 3D 问题和这期传达的知识点。

内容路径：网站找论文 → 自动交给 Claude → 提炼一个知识点 → 写解释逻辑 → three.js 三维图解 → 解说与动画同步 → 人工核对原文和观众理解。先画原来的困难，再演解决过程，最后对比改进；图解示意不能冒充论文实测结果。

验收重点：观众是否知道“解决了什么 3D 问题”，是否能复述“传达了哪个 3D 知识点”。以下保留的工程资料是制作支撑，不再作为 PPT 的七个核心问题，也不以省 token 作为栏目的主要价值。

输入与契约：sources.json 指定素材来源，episode.json 写选题、口播、镜头与文案。校验通过后再交给生产代码；模型可以更换，数据格式保持一致。

路径：3d-board 选题 → 核对原文 → 模型写两个 JSON → 校验 → 后台浏览器采集清洗 → 配音或真人录音 → 词时间戳对齐 → 模板与 three.js 场景逐帧渲染 → 合成 → 平台文案 → 人审。

制作支撑资料（供工程交接，不作为七项核心问题讲述）：

1. 数据契约将模型和生产分开，代码校验拦住格式或字段错误。
2. 后台浏览器抓原文图片、说明、官方视频，录页面和 3D 查看器，并过滤无关图片。用户提供的第 2 期记录：96 个文件清洗后保留 60 个。
3. 固定外壳、可扩展镜头库、每期数据分层；固定随机种子、按词时间点逐帧渲染。用户提供的第 1 期回归记录相似度为 0.990，不将这一案例扩大为所有环境下逐像素相同的保证。
4. three.js 场景由时间驱动，已有场景复用，不必每期让模型重新写动画。
5. 同一份词时间戳驱动字幕、镜头与配乐卡点；AI 配音和真人录音共用对齐流程，真人录音变速上限 1.1 倍，仍需试听。
6. 一份数据生成 8 个平台的发布文案，代码检查字数；平台按配置扩展，不等于自动发布。
7. 逐步记录进度，每个阶段人审后继续；不自动发布，密钥不写进内容、日志或交付文件。

为什么选 3D 论文：有明确的问题，空间关系或变化适合用三维动画解释，原文可核对。自建网站接起资料入口；栏目面向普通观众解释知识，业务上为 Tripo 积累 3D 专业认知。

最终 Skills：固定数据契约、采集与清洗规则、模板和场景复用、词时间戳与渲染规范、平台配置、人审和安全、回归检查。三个核心是 token 与生产分开、镜头场景持续积累、修改模板后能检查风格和结果是否退化。

运行环境按用户提供的工程说明为 Python、Node、Chrome、FFmpeg；无需额外依赖包的描述限定于该工程已配置环境，不能理解为所有电脑不需要准备环境。本页不编造未提供的目录或入口命令，接入时以实际工程包说明为准。

## 03 HolyMolly

定位：把一个游戏想法做成可分发的展示视频。重点是减少重复录屏和剪辑、准确呈现玩法、保留创作者口吻；人工确认后再分发，传播效果另行验证。

九步流程：聊想法 → 写游戏提示词 → 生成首尾参考图 → HolyMolly 构建 → 自动试玩与录屏 → 解说词与配音 → 视觉包装 → 分层合成 → 质检出片。Claude Code 组织流程，人确认想法、提示词、参考图、解说、声音、风格和成片。

自动试玩：不是大模型每帧看图打游戏。游戏提供状态接口（仪表盘），规则程序按状态操作或调用自动演示（方向盘），游戏时间每次推进 1/30 秒后采集（暂停键）。Playwright / Chrome 操作网页，逐帧保存画面，每半秒记状态；状态记录帮助找关键片段，录后检测静止位置。

适配边界：游戏要留接口；新游戏的操作规则和网页改版后的按钮定位可能需要更新。自动提交不通时可手动提交，再提供游戏链接。

口播：创作者第一人称，先给结局，再倒带讲过程；只用真实发生的画面和有记录的数字。ElevenLabs 先试三种语气，人选一种后整篇生成，只在开头给语气指令，保留正常停顿。音高音量指标只做初筛，人听完才确认。

最终制作：词时间点同时驱动游戏片段、字幕贴纸与音效。底层玩法画面做变速、倒放和慢放补帧，中层用 HTML 做标题卡片，声音单独混合，FFmpeg 合成 MP4。开头三秒不进音乐，人声时背景音乐让路，音效只跟真实事件并加过渡。

质检：按工程设置检查 30–35 秒、约 −15 LUFS、稿声一致、语气连续、开头交代结果、画面无明显卡顿；出每秒一帧总览，再人工完整看听。不是只靠一个指标自动保证质量。

沉淀 Skills：选真实变化、创作者口吻、按词驱动的包装模板、剪辑和声音检查。雪球结尾曾用到通关后静止的片段；只重做游戏画面，改用静止前片段并检查补帧，保留字幕、卡片、配音和音乐。随后新增静止检测、慢放检查和卡顿质检规则。

使用：用 Claude Code 打开工程，先跑不需要 key 的 demo，确认环境后配置个人配音和生图凭据、登录 HolyMolly；从一个游戏开始验证。

验证范围：补充文档明确，雪球案例已验证解说到成片；换新游戏的全流程与 Windows 仍待实测。网页样片为已有真实成片，本次没有重新运行生产线。片中的 11m 50s、53 口为原案例记录，不是其他游戏的保证。

## 同事第一次怎么接

1. 说清楚你要给谁看，以及观众看完应该知道或做什么。
2. 从三条产线中选最近的一条，提供一份可用素材或一个玩法。
3. 与 Kevin 对齐工程版本、账号权限、素材使用范围与人工确认点。
4. 先跑一条，从头看完、听完；记录耗时、返工和问题。
5. 发布后记录流量与有效反馈；如需评估业务价值，再接入点击、注册、使用等归因。
6. 只把经核实且可复用的经验写回 Skills，保留版本。
